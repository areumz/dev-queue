# v2-0c-2 비밀번호 찾기·이메일 인증 설계

> 상위 문서: [v2-0 개요](README.md) · 앞 단계: [c-1 마이페이지](c1-mypage-brainstorming.md)
> 목표: **이메일 소유를 인증 메일로 확인**하고, 인증된 이메일로 **비밀번호를 잊은 사용자가 스스로 재설정**할 수 있다.

---

## 0. 이번 단계의 목적

c-1에서 `User.email`을 선택 입력으로 추가했다. 하지만 그 이메일은 **인증 없이 저장**돼서 "정말 그 사람 메일인지" 모른다.
c-2에서 두 가지를 한꺼번에 만든다. 둘이 같은 "메일 발송 + 1회용 토큰" 구조를 쓰기 때문이다.

1. **이메일 인증:** 메일 속 링크를 눌러야 "인증됨"이 된다.
2. **비밀번호 찾기:** 인증된 이메일로만 재설정 링크를 보낸다.

프론트로 치면 두 기능 모두 "일회용 로그인 링크(매직 링크)"와 같은 원리다. 메일함에 들어갈 수 있는 사람만 링크를 볼 수 있다는 점이 증거가 된다.

---

## 1. 범위

**넣는 것**

- 이메일을 저장(가입, 마이페이지)하면 **인증 메일이 자동 발송**된다. 마이페이지에서 재발송할 수 있다.
- `GET /verify-email?token=...`: 링크를 누르면 인증 완료.
- `GET/POST /forgot-password`: 이메일을 입력하면 재설정 메일 발송(항상 같은 응답).
- `GET/POST /reset-password`: 링크로 들어와 새 비밀번호 설정.
- 메일 발송 틀(`MailSender` 인터페이스), 1회용 토큰 저장·검증, 사용자(이메일) 단위 발송 횟수 제한.
- **`/forgot-password`의 메일 처리는 응답과 분리(`@Async`)한다.** 응답 시간으로 가입 여부가 드러나지 않게 한다(이슈 6).
- **설정 누락 방지:** `app.mail.enabled`가 없으면 앱이 시작되지 않는다(이슈 7).
- 배포 후 확인: 인증 메일 수신, 인증 링크, 비밀번호 재설정, 만료·재사용 링크.

**넣지 않는 것 (이유)**

- SNS 로그인 → c-3.
- 같은 IP 단위 횟수 제한 → d. 이번엔 이메일(사용자) 단위만 한다.
- 비밀번호를 바꿨을 때 다른 기기 세션 끊기 → c-1에서 정한 한계 그대로. 로그인 방식이 늘어나는 c-3 또는 d 이후에 다시 판단한다.
- HTML 디자인 메일, 영속 메일 큐, 재시도 → 이번엔 텍스트 메일을 보낸다. 마이페이지 인증 메일은 즉시 발송하고 실패하면 안내한다. 비밀번호 찾기 메일은 메모리 큐(`@Async`)로 보내고 실패는 로그로만 남긴다.
- 계정 복구(인증된 이메일이 없는 사용자) → 방법이 없다. 알려진 한계로 적는다.

## 3. 이슈와 해결

### 이슈 1. 인증 안 된 이메일을 믿을 수 없다

**문제.** c-1의 이메일은 아무 주소나 적어도 저장된다. 비밀번호 찾기를 여기에 연결하면, 남의 이메일을 등록한 사람이 비밀번호 재설정 메일을 받을 수 있는 구조가 된다.

**해결.** 비밀번호 찾기는 **`emailVerified = true`인 이메일에만** 메일을 보낸다. 이메일을 바꾸면 `false`로 돌아간다.

### 이슈 2. 이메일 선점과 중복

**문제.** c-1은 인증 여부와 상관없이 이메일 중복을 막았다. 누군가 `bob@x.com`을 인증 없이 먼저 등록하면, 진짜 bob은 등록할 수 없다.

**해결.** 인증된 이메일만 유일하게 한다. 미인증 이메일은 여러 계정이 같은 값을 가질 수 있고, 먼저 인증을 끝낸 계정이 가져간다. 비밀번호 찾기는 "인증된 이메일"로만 계정을 찾아서 항상 한 계정으로 정해진다.

### 이슈 3. 메일을 마구 보내게 만들 수 있다

**문제.** 비밀번호 찾기에 이메일만 넣으면 메일이 간다. 누군가 남의 이메일로 반복해서 누르면 그 사람 메일함이 가득 차고, 하루 500통 제한도 금방 소진된다. 진짜 사용자가 메일을 못 받게 된다. 링크드인 등에 공개하면 더 현실적이다.

**해결.** 같은 사용자·같은 종류의 메일은 **1시간에 3회**까지만 보낸다. `email_token`의 `createdAt`을 세므로 별도 테이블이 필요 없다. 제한에 걸려도 화면 문구는 똑같다(제한 여부가 가입 여부를 알려주면 안 된다).

### 이슈 4. 토큰이 새면 계정이 뚫린다

**문제.** 토큰은 사실상 임시 비밀번호다. DB가 새거나 링크가 오래 살아 있으면 위험하다.

**해결.**

- 안전한 난수 32바이트. 메일 링크에는 원본, DB에는 **SHA-256 해시만** 저장한다.
- 만료: 인증 24시간, 비밀번호 재설정 30분.
- **1회용:** 쓰면 `usedAt`을 채운다.
- 새 토큰을 만들면 같은 사용자·같은 종류의 이전 토큰은 무효 처리한다(재발송하면 옛 링크는 못 쓴다).
- 비밀번호 재설정 성공 시 그 사용자의 열린 토큰을 모두 무효화한다.
- 토큰 실패(없음, 만료, 이미 사용)는 이유를 구분하지 않고 한 가지 안내 페이지를 보여준다.

### 이슈 5. 공개 서비스에서 http 링크는 위험하다

**문제.** 지금 서비스는 http다. 재설정 링크(`http://...?token=...`)가 암호화 없이 오가면 같은 네트워크의 제3자가 토큰을 볼 수 있다.

**해결.** 토큰이 짧게 만료되고 1회용이라 피해는 줄지만 근본 해결은 아니다. **HTTPS 적용을 c-2 배포 전 필수 조건으로 둔다.** 배포 순서는 **HTTPS 적용 → c-2 배포**다(7장). DuckDNS도 Let's Encrypt로 무료 HTTPS를 붙일 수 있다. 코드가 아니라 서버 설정 작업이다. 앱도 `app.mail.enabled=true`인데 `app.base-url`이 `https://`가 아니면 시작되지 않게 해서 순서를 어기기 어렵게 한다.

### 이슈 6. 응답 시간으로 가입 여부가 드러난다

**문제.** `/forgot-password`가 가입된(인증된) 주소에만 메일을 보내고 응답 문구는 같게 해도, **응답 시간**이 다르다. 메일을 보내는 쪽은 SMTP 통신 때문에 수백 밀리초에서 수 초가 걸리고, 없는 주소는 바로 끝난다. 시간을 재면 가입 여부를 알 수 있다. 프론트로 치면 에러 문구를 감춰도 네트워크 탭의 응답 시간이 답을 알려주는 상황이다.

**판단: 분리한다.** 문구를 같게 만든 이유와 같은 목적이고, 비용이 작다. `@Async`로 **계정 조회, 토큰 발급, 횟수 제한 확인, 발송까지 통째로** 다른 스레드로 넘기고 컨트롤러는 바로 같은 응답을 준다. 발송만 분리하면 DB 조회·토큰 발급 시간 차이가 남는다.

**지킬 점.**

- 전용 실행기(`mailExecutor`)를 둔다. 스레드 2개, 대기 큐 100개로 제한하고, 가득 차면 요청을 버리고 경고 로그만 남긴다(메일 폭탄이 서버 자원을 먹지 않게). 응답은 그대로다.
- 비동기 안의 예외는 호출한 쪽으로 전달되지 않는다. 실패는 **토큰·링크를 뺀 채** 로그로만 남긴다. 사용자에게 알릴 방법이 없다는 점은 한계로 적는다.
- 인증 메일(마이페이지)은 분리하지 않는다. 로그인한 본인의 이메일이라 가입 여부 노출 문제가 없고, 실패를 바로 안내해야 한다.
- 응답 시간이 완전히 같아지는 것은 아니다. 큐에 넣는 시간 정도의 차이는 남지만 SMTP·DB 시간 차이는 사라진다.

**테스트에서 비동기를 다루는 법.**

- **기본: 동기 실행기로 바꾼다.** `test` 프로필에서는 `mailExecutor`를 `SyncTaskExecutor`로 만든다. 그러면 `@Async` 메서드도 호출한 스레드에서 끝나서, 기존 통합 테스트(`@Transactional`, 롤백)가 그대로 동작하고 "메일이 모였는지"를 바로 확인할 수 있다. (`@Profile("!test")`는 진짜 실행기, `@Profile("test")`는 동기 실행기 — 같은 이름의 빈을 덮어쓰지 않고 프로필로 나눈다. Spring Boot는 빈 덮어쓰기가 기본 꺼져 있다.)
- **비동기 계약 테스트 1개.** 진짜 실행기와 "latch로 멈추는 가짜 `MailSender`"를 쓴다. 요청이 **발송이 끝나기 전에 응답한다**는 것과, latch를 풀면 메일이 도착한다는 것을 증명한다. 다른 스레드는 테스트의 미커밋 데이터를 볼 수 없어서 이 테스트만 `@Transactional`을 쓰지 않고, 만든 데이터를 스스로 지운다.
- 큐가 가득 찼을 때 요청을 버리는 동작은 실행기를 작게 만든 단위 테스트로 확인한다.

### 이슈 7. 설정을 빠뜨리면 운영에서 토큰이 로그에 남는다

**문제.** `LogMailSender`는 메일 내용(링크와 토큰 포함)을 로그로 출력한다. "기본값이 `LogMailSender`"이면, 운영에서 `app.mail.enabled=true`를 빠뜨려도 앱이 정상 기동하고, 사용자에게는 메일이 갔다고 보이는데 실제로는 로그에 토큰이 남는다. 로그에 접근하는 사람은 누구든 계정을 탈취할 수 있다.

**해결.** `app.mail.enabled`에 **기본값을 두지 않는다.** 값이 없으면 앱이 시작되지 않는다. `LogMailSender`는 `false`를 **명시했을 때만** 쓴다.

- `application.properties`에는 이 값을 넣지 않는다.
- `application-local.properties.example`과 테스트의 `application-test.properties`에 `app.mail.enabled=false`를 **명시**한다.
- 운영은 `true`로 환경 변수에 둔다. 이때 `spring.mail.host`가 없으면 `SmtpMailSender`를 만들 수 없어 역시 시작되지 않는다.
- `app.base-url`도 기본값을 두지 않고, `enabled=true`이면 `https://`로 시작해야 한다.
- `true`·`false`가 아닌 값(오타)도 시작 단계에서 실패한다.

### 알려진 한계

- **다른 기기의 세션은 비밀번호를 재설정해도 유지된다.** (c-1과 같음. 세션을 모두 끊는 방식은 c-3 또는 d 이후에 판단)
- **인증된 이메일이 없는 계정은 비밀번호를 잃으면 복구할 방법이 없다.**
- **인증 링크는 GET으로 상태를 바꾼다.** 토큰이 1회용이라 안전하지만, 메일 앱이 링크를 미리 열어보면 토큰이 소진될 수 있다. 확인 버튼(POST) 중간 화면을 두는 방식은 이번에 하지 않는다.
- **횟수 제한은 이메일(사용자) 단위뿐이다.** IP 단위 제한은 d로 넘긴다.
- **마이페이지의 인증 메일 발송은 동기다.** 메일 서버가 느리면 그 요청이 느려진다(타임아웃을 짧게 둔다). 비밀번호 찾기만 비동기다.
- **비밀번호 찾기 메일은 재시도하지 않고, 실패해도 사용자는 모른다.** 비동기라 발송이 실패하면 로그에만 남는다. 사용자는 메일이 안 오면 다시 요청해야 한다(횟수 제한 안에서). 서버가 꺼지는 순간 대기 중이던 메일은 사라진다(영속 큐 없음).
- **응답 시간이 완전히 같지는 않다.** 큐에 넣는 시간 차이는 남는다. 가입 여부를 알아내기에는 너무 작다고 판단했다.
- **큐가 가득 차면(대기 100개) 요청을 버린다.** 메일 폭탄 때 진짜 사용자의 요청도 버려질 수 있다. IP 단위 제한(d)으로 줄인다.
- Gmail 하루 발송 한도(약 500통)와 발신자 표시가 개인 Gmail인 점. 사용자가 늘면 SES 등으로 교체한다.

## 4. 설계

### 4-1. 데이터

- **`User.emailVerified`** (boolean, 기본 false). 이메일을 처음 저장하거나 바꾸면 false가 된다. 이메일이 비어 있으면 false다.
- **새 테이블 `email_token`**

| 컬럼        | 설명                                                                    |
| ----------- | ----------------------------------------------------------------------- |
| `id`        | PK                                                                      |
| `userId`    | 소유자. `Vocabulary.articleId`와 같이 FK 없는 Long (프로젝트 기존 방식) |
| `type`      | `VERIFY_EMAIL` 또는 `RESET_PASSWORD`                                    |
| `tokenHash` | SHA-256 해시(hex). 조회용 인덱스                                        |
| `expiresAt` | 만료 시각 (`Clock` 빈 사용, 기존 `Asia/Seoul`)                          |
| `usedAt`    | 사용 시각. null이면 미사용                                              |
| `createdAt` | 발급 시각. 횟수 제한에 쓴다                                             |

- 인증 링크의 이메일 값은 토큰에 넣지 않는다. 토큰으로 사용자를 찾고, 인증하는 순간 **그 사용자의 현재 이메일**을 인증한다. 토큰 발급 뒤 이메일을 바꿨다면, 바꿀 때 이전 VERIFY 토큰이 무효화되므로 안전하다.

### 4-2. 코드 구조 (기존 규칙 그대로)

- **`MailSender`** 인터페이스(외부 서비스는 인터페이스 뒤에). 구현 두 개:
  - `LogMailSender`: 메일 내용을 로그로 출력한다. **`app.mail.enabled=false`를 명시했을 때만** 쓴다. 로컬·테스트용.
  - `SmtpMailSender`: `app.mail.enabled=true`일 때 쓴다. `spring-boot-starter-mail` 사용.
  - 둘 중 무엇을 쓸지는 `MailConfig`가 `@Value("${app.mail.enabled}")`(기본값 없음)로 정한다. 값이 없거나 `true`·`false`가 아니면 시작이 실패한다. `true`인데 `app.base-url`이 `https://`가 아니면 역시 실패한다.
- **`AsyncConfig`**: `@EnableAsync`와 `mailExecutor`(스레드 2, 큐 100, 가득 차면 버리고 경고 로그). `@Profile("!test")`는 진짜 실행기, `@Profile("test")`는 `SyncTaskExecutor`. `@Async("mailExecutor")`가 붙는 곳은 `PasswordResetService.requestReset` 하나뿐이다. 비동기 예외는 토큰·링크를 뺀 로그로만 남긴다.
- **`EmailTokenRepository`**: `repository/` 인터페이스 + `repository/jpa/` 구현 + `SpringDataJpa*` + `memory/` (4곳 패턴).
- **`TokenService`**: 발급, 해시, 이전 토큰 무효화, 검증(만료·1회용), 횟수 제한.
- **`EmailVerificationService`**: 인증 메일 발송, 링크 확인, 인증 시 중복 검사.
- **`PasswordResetService`**: 재설정 메일 발송(조용히 무시 규칙 포함), 토큰으로 비밀번호 변경.
- Controller는 얇게. 비즈니스 로직은 Service에 둔다.
- 링크 주소는 `app.base-url` 설정으로 만든다.
- **Security 설정:** 로그인 없이 접근을 허용하는 경로는 `/verify-email`, `/forgot-password`, `/reset-password` 세 개뿐이다.

### 4-3. 규칙

- **인증 메일 발송:** 가입·마이페이지에서 이메일이 새로 저장되거나 바뀔 때. 발송이 실패해도 **저장은 성공**하고 "메일을 보내지 못했어요. 마이페이지에서 다시 보내 주세요"를 안내한다.
- **인증 확인:** 토큰이 유효하면 그 사용자의 이메일을 인증한다. **그 이메일을 이미 다른 계정이 인증했으면** "이미 다른 계정에서 인증된 이메일입니다"를 보여주고 인증하지 않는다.
- **비밀번호 찾기 요청:** 컨트롤러는 입력값을 `PasswordResetService.requestReset`(`@Async`)에 넘기고 **바로** 같은 화면을 응답한다. 비동기 안에서 입력한 이메일로 **인증된** 계정이 있을 때만 토큰을 만들고 메일을 보낸다. 없거나 미인증이거나 횟수 제한에 걸려도 화면은 같고, 응답 시간도 DB·SMTP 시간에 영향받지 않는다.
- **재설정:** 토큰 확인 → 새 비밀번호(`@ValidPassword`, c-1 규칙 그대로) → 저장 → 열린 토큰 전부 무효화 → `/login?reset`.
- **기존 사용자:** c-1에서 이메일을 등록한 사용자는 `emailVerified = false`로 시작한다. 마이페이지에서 재발송으로 인증한다. 자동으로 메일을 보내지 않는다.
- c-1의 `checkEmailAvailable`(저장 시 중복 검사)은 제거하고, 인증 시 검사로 옮긴다. 이메일 조회 메서드는 "인증된 것만" 찾도록 바꾼다.

## 5. Task 순서

1. **메일 발송 틀:** `MailSender`, `LogMailSender`, `SmtpMailSender`, `MailConfig`(설정이 없으면 시작 실패), `AsyncConfig`(`mailExecutor`), `spring-boot-starter-mail`, `app.base-url`, `application-local.properties.example`에 `app.mail.enabled=false`와 Gmail 예시, `application-test.properties`에 `app.mail.enabled=false`·`app.base-url`. 테스트용 가짜 `MailSender`(메일을 모아둠). **`app.mail.enabled`는 `application.properties`에 넣지 않는다.**
2. **토큰:** `EmailToken`, Repository 4곳, `TokenService`(발급·해시·무효화·검증·횟수 제한).
3. **이메일 인증:** `User.emailVerified`, 저장 시 발송, 마이페이지 표시·재발송, `GET /verify-email`, 중복 검사 이동, c-1 중복 관련 테스트 수정.
4. **비밀번호 찾기:** `/forgot-password`(`requestReset`은 `@Async`), `/reset-password`, 로그인 화면 링크와 `?reset` 안내, README 갱신.

## 6. 테스트

- **토큰:** 만료되면 실패, 두 번 쓰면 실패, 새로 발급하면 이전 토큰 무효, DB에는 해시만 저장, 1시간 4번째 요청은 발송 안 됨.
- **인증:** 저장하면 메일이 감, 이메일을 바꾸면 미인증으로 돌아가고 이전 토큰 무효, 링크를 누르면 인증됨, 이미 다른 계정이 인증한 이메일이면 실패, 메일 발송이 실패해도 저장은 성공, 비로그인 상태에서도 링크가 동작.
- **중복 규칙:** 미인증 이메일은 여러 계정이 가질 수 있음, 한 계정이 인증하면 다른 계정은 같은 이메일을 인증할 수 없음.
- **비밀번호 찾기:** 등록된 주소와 없는 주소의 응답이 같음, 미인증 주소에는 메일이 안 감, 재설정 후 새 비밀번호로 로그인되고 옛 비밀번호는 실패, 사용한 링크는 재사용 불가, 비밀번호 규칙 위반은 거부, 재설정 성공 시 다른 열린 토큰 무효.
- **비동기:**
  - 기본 통합 테스트는 `test` 프로필의 `SyncTaskExecutor`로 돌아서 `@Transactional` 롤백과 그대로 맞는다.
  - **계약 테스트 1개:** 진짜 실행기 + latch로 멈추는 가짜 `MailSender`로, 요청이 발송 완료 전에 응답하고 latch를 풀면 메일이 도착함을 확인한다. 이 테스트만 `@Transactional`을 쓰지 않고 데이터를 직접 지운다.
  - 큐가 가득 차면 요청을 버리고 응답은 그대로임(작은 실행기를 쓰는 단위 테스트). 비동기 안의 예외가 토큰을 로그에 남기지 않음.
- **설정(`ApplicationContextRunner`):**
  - `app.mail.enabled`가 없으면 컨텍스트 시작 실패
  - `true`·`false`가 아닌 값이면 실패
  - `false`면 `LogMailSender`, `true`면 `SmtpMailSender`
  - `true`인데 `app.base-url`이 `https://`가 아니면 실패
  - `true`인데 `spring.mail.host`가 없으면 실패
  - `application-test.properties`에 `false`가 명시돼 있어 기존 통합 테스트가 그대로 뜬다
- **보안:** POST는 CSRF 없으면 403, 허용 경로는 세 개뿐이고 나머지는 여전히 로그인 필요, 토큰 실패 사유가 구분되지 않음.

## 7. 별도로 해야할 일

- **Gmail 앱 비밀번호 발급:** 2단계 인증을 켜고 앱 비밀번호를 만든다. 코드나 저장소에 넣지 않고 `application-local.properties`(gitignore)와 서버 환경 변수에만 둔다.
- **HTTPS 적용(c-2 배포 전 필수):** DuckDNS 도메인에 Let's Encrypt 인증서를 붙인다. http로는 재설정·인증 링크의 토큰이 암호화 없이 오가므로 c-2를 배포하지 않는다.
- **배포 순서: ① HTTPS 적용·확인 → ② c-2 배포.**
  1. HTTPS를 붙이고 `https://` 주소로 로그인·글 목록이 정상인지 확인한다.
  2. 서버 환경 변수에 `APP_MAIL_ENABLED=true`, `APP_BASE_URL=https://...`, Gmail SMTP 설정(`SPRING_MAIL_*`)을 넣는다. 하나라도 빠지면 앱이 시작되지 않으므로 **시작 실패 로그가 설정 점검 신호**다.
  3. c-2를 배포한다.
  4. http로 들어오는 요청은 https로 돌려보내는 것을 확인한다(서버 설정).
- **로컬 설정 갱신:** 기존 `application-local.properties`(gitignore)에 `app.mail.enabled=false`와 `app.base-url=http://localhost:8080`을 추가한다. 없으면 로컬 앱도 시작되지 않는다.
- **EC2 Java 25 업그레이드**(v2-0a에서 이월).
- **Gmail 앱 비밀번호**는 서버 환경 변수에만 둔다(위 항목 참고).
- **배포 후 확인:** 가입(이메일 있음/없음), 인증 메일 수신과 링크, 재발송 버튼, 비밀번호 찾기 메일, 만료·재사용 링크 안내, 기존 사용자의 미인증 표시.

## 8. 위험

- **`emailVerified` 컬럼 추가:** `ddl-auto=update`로 NOT NULL 컬럼이 추가된다. MySQL이 기존 행을 0(false)으로 채우는지 배포 전에 로컬 DB로 확인한다.
- **메일 발송 실패·지연:** 마이페이지 인증 메일은 동기라 SMTP가 느리면 그 요청이 느려진다. 타임아웃을 짧게 설정하고, 실패해도 가입·저장은 성공하게 한다. 비밀번호 찾기는 비동기라 응답은 느려지지 않는다.
- **스팸함:** 개인 Gmail 발신이라 메일이 스팸함에 갈 수 있다. 화면에 "스팸함도 확인해 주세요"를 안내한다.
- **토큰 로그 노출:** `LogMailSender`는 링크(토큰 포함)를 로그에 남긴다. 로컬·테스트 전용이다. `app.mail.enabled`에 기본값이 없어서 운영에서 설정을 빠뜨리면 앱이 시작되지 않는다(이슈 7). 단, **운영에서 `false`로 잘못 명시하면** 막을 수 없으므로 배포 체크리스트에 값 확인을 넣는다.
- **설정 누락으로 인한 시작 실패:** 의도된 동작이다. 로컬 `application-local.properties`를 갱신하지 않으면 로컬도 시작되지 않는다(7장).
- **비동기 오류가 조용히 사라진다:** 비밀번호 찾기 메일 실패는 로그로만 남는다. 로그에서 실패 건수를 볼 수 있게 경고 로그 문구를 고정한다(토큰·이메일 원문은 뺀다).
- **비동기 테스트의 불안정성:** 계약 테스트 1개만 진짜 스레드를 쓴다. 시간 대기가 아니라 latch로 순서를 고정해서 흔들리지 않게 한다.
- **c-1 코드 변경:** 저장 시 중복 검사를 없애므로 c-1 테스트 일부가 바뀐다. 의도된 변경이지만 리뷰 때 확인한다.

## 9. 완료 기준

1. 이메일을 저장하면 인증 메일이 가고, 링크를 누르면 인증된다. 마이페이지에 상태와 재발송 버튼이 있다(테스트).
2. 이메일을 바꾸면 미인증으로 돌아가고 이전 인증 링크는 무효다(테스트).
3. 미인증 이메일은 여러 계정이 가질 수 있고, 인증은 먼저 끝낸 계정이 가져간다(테스트).
4. 비밀번호 찾기는 인증된 이메일에만 메일을 보내고, 어떤 경우에도 화면 응답이 같다(테스트).
5. 재설정 링크는 만료되고, 한 번만 쓸 수 있고, 새 발급이 이전 링크를 무효화한다(테스트).
6. 재설정 후 새 비밀번호로 로그인된다. 비밀번호 규칙은 c-1과 같다(테스트).
7. 같은 사용자에 대해 같은 종류의 메일은 1시간에 3회를 넘지 않는다(테스트).
8. 허용 경로 세 개를 빼면 로그인이 필요하고, POST는 CSRF가 필요하다(테스트).
9. 비밀번호 찾기 요청은 발송 완료를 기다리지 않고 응답한다(계약 테스트). 기본 테스트는 동기 실행기로 돈다.
10. `app.mail.enabled`가 없으면 앱이 시작되지 않고, `LogMailSender`는 `false`일 때만 쓰인다. 테스트 설정에 명시돼 있다(테스트).
11. 7장에 "HTTPS 적용 → c-2 배포" 순서와 환경 변수 목록이 적혀 있다. `enabled=true`인데 `app.base-url`이 `https://`가 아니면 시작되지 않는다(테스트).
12. CI(`code-quality`)가 통과한다.
13. README의 c-2 행이 갱신돼 있고, c-3·d로 넘기는 숙제(세션 끊기, IP 제한, 큐·재시도)가 기록돼 있다.

# v2-0c-1 마이페이지 설계

> 상위 문서: [v2-0 개요](README.md)
> 목표: 로그인한 사용자가 **자기 정보(닉네임, 직군, 이메일, 비밀번호)를 직접 고치고**, 원하면 **탈퇴**할 수 있다. 닉네임을 바꾸면 화면에도 바로 반영된다.

---

## 0. 이번 단계의 목적

b에서 Spring Security(폼 로그인, CSRF, 세션 `LoginUser`)를 넣어서 "누구인지"를 확인하는 단계는 끝났다. 하지만 사용자가 자기 정보를 고칠 방법이 없어서 해당 부분을 개선하는 작업을 진행한다.

c는 범위가 커서 셋으로 나눈다. 각각 브레인스토밍 → 설계 승인 → 계획 → 구현 → PR → 머지 사이클을 돈다.

| 단계              | 내용                                                            | 외부 서비스         |
| ----------------- | --------------------------------------------------------------- | ------------------- |
| **c-1 (이 문서)** | 마이페이지: 정보 수정, 비밀번호 변경, 탈퇴, 이메일 칸 추가      | 없음                |
| c-2               | 비밀번호 찾기: 메일 발송, 만료되는 1회용 토큰, 이메일 소유 확인 | 메일 서버           |
| c-3               | SNS 로그인(OAuth2)                                              | 구글·GitHub 앱 등록 |

c-2는 c-1이 만든 이메일 칸이 있어야 하고, c-3은 c-2까지 끝난 계정 구조 위에서 "SNS 계정과 기존 계정을 어떻게 연결할지"를 정한다. 그래서 순서를 지킨다. c-3은 외부 앱 등록이 필요해서 그때 가서 "지금 할 가치가 있는가"를 다시 판단한다.

## 1. 범위

**넣는 것**

- `GET/POST /mypage`: 닉네임, 직군(`role`, `roleDetail`), 이메일 수정. 아이디는 읽기 전용.
- `GET/POST /mypage/password`: 현재 비밀번호 확인 후 새 비밀번호로 변경.
- `POST /mypage/withdraw`: 비밀번호 재입력 후 탈퇴(완전 삭제).
- 가입 폼: 이메일(선택) 입력과 안내문.
- 상단 메뉴: 닉네임을 누르면 마이페이지로 가는 링크.
- b에서 넘어온 숙제: 닉네임을 바꾸면 세션의 `LoginUser`도 같이 갱신.

**빼는 것**

- **이메일 소유 확인(인증 메일)** → c-2. 메일 발송 구조를 비밀번호 찾기와 한 번만 만들기 위해서다. c-1의 이메일은 **저장만 하고 어떤 기능에도 연결하지 않는다.** 그래서 인증 전의 이메일이 위험해지지 않는다.
- **`email`·`username` DB 유니크 제약** → d. 테이블 변경 도구(Flyway)와 함께 처리한다. c-1은 앱 코드에서만 중복을 검사하므로 동시 요청에는 약하다(b의 `username`과 같은 한계).
- **`GET /articles`를 열기만 해도 오늘의 팝업이 소진되는 문제** → 이후 결정(제품 정책 문제이고 테이블 변경이 필요하다).
- 프로필 사진, 아이디 변경 → 하지 않는다.

## 3. 이슈와 해결

### 이슈 1. 닉네임을 바꿔도 화면은 안 바뀐다

**왜 문제인가.** 로그인할 때 세션에 `LoginUser`(id, 아이디, 닉네임) 복사본이 저장된다. 마이페이지에서 DB의 닉네임을 바꿔도 이 복사본은 그대로라서, 상단에는 다음 로그인까지 옛 닉네임이 보인다. 프론트로 치면 서버 데이터는 바꿨는데 클라이언트 스토어를 갱신하지 않은 상태다.

**해결 방법 비교**

| 방법                                 | 내용                                                              | 평가                                                                                                                                                                                                |
| ------------------------------------ | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. 세션의 `LoginUser` 교체(채택)** | 저장 직후 새 `LoginUser`를 만들어 `SecurityContext`에 바꿔 넣는다 | 코드가 몇 줄이고 DB를 더 읽지 않는다. 로그인 상태와 세션 ID는 유지된다. b의 "세션에는 최소 정보만" 방향과 맞고, c-3에서 로그인 방식이 늘어도 "로그인 정보를 한 곳에서 만든다"는 구조를 지키기 쉽다. |
| B. 세션에 닉네임을 안 둠             | 화면을 그릴 때마다 DB에서 읽는다                                  | 항상 최신이지만 요청마다 쿼리가 늘고, 상단 표시를 모든 컨트롤러가 챙겨야 한다.                                                                                                                      |
| C. 변경 후 강제 로그아웃             | 다시 로그인하게 한다                                              | 가장 쉽지만 닉네임만 바꿔도 다시 로그인해야 해서 불편하다.                                                                                                                                          |

**비밀번호를 바꿀 때는** 지금 쓰고 있는 브라우저의 세션 ID를 새로 발급한다. 이 방어는 **현재 브라우저에만** 해당한다. 비밀번호를 바꾸기 전에 누군가 이 브라우저의 세션 ID를 훔쳤다면 새 ID로 바뀌어 그 ID가 쓸모없어진다는 의미다. **다른 기기·다른 브라우저의 로그인 세션은 그대로 유지된다**(아래 "알려진 한계" 참고).

### 알려진 한계: 다른 기기의 세션은 유지된다

**무엇이 문제인가.** 로그인 상태(세션)는 서버가 기기·브라우저마다 따로 들고 있다. 비밀번호를 바꾸거나 탈퇴해도 **지금 쓰는 브라우저의 세션만** 새로 발급되거나 끊기고, 다른 기기의 세션은 그대로 로그인 상태다.

- **비밀번호 변경 후:** 분실한 기기나 남이 로그인해 둔 브라우저가 계속 로그인된 상태로 남는다. 비밀번호를 바꾸는 이유가 "계정이 위험해서"일 때 이 점이 아쉽다.
- **탈퇴 후:** 다른 기기에서는 계정이 지워졌는데도 세션이 살아 있다. 그 세션으로 다른 화면(글 목록, 마이페이지)을 열면 404 페이지가 나온다. 데이터는 이미 지워져서 유출은 없다. 다만 그 세션으로 새 글 저장(POST /articles)은 막히지 않는다. `ArticleService.create`가 사용자가 아직 있는지 확인하지 않고 `Article.userId`에 외래키도 없어서, 주인 없는 글이 생길 수 있다. `SessionRegistry`나 DB 세션을 붙일 때까지 남는 한계다.

**`SessionRegistry`로 모든 세션을 끊는 방안은 c-1에서 하지 않는다.**

- `SessionRegistry`는 "누가 어떤 세션을 갖고 있는지" 서버 메모리에 기록하는 Spring Security 장치다. 이것으로 비밀번호 변경·탈퇴 때 그 사용자의 모든 세션을 만료시킬 수 있다.
- 쓰려면 세션 관리 설정(동시 세션 제어)을 추가해야 하고, 로그인·로그아웃 이벤트와 연결하는 설정이 필요해서 Security 설정 구조를 건드린다.
- c-1의 목적은 마이페이지다. 세션 전체 관리는 별도 주제이고 c-3(SNS 로그인)에서 로그인 방식이 늘면 함께 다시 보는 편이 낫다.
- **대안(나중에):** 세션을 DB에 저장하는 방식(Spring Session)은 재시작에도 살아남고 사용자별 세션 삭제가 쉽다. 이 선택은 서버 구성(배포 구조)과 함께 d 이후에 판단한다.

그래서 c-1은 "현재 브라우저만 처리"로 정하고, 이 한계를 PR 본문과 README의 넘기는 것에 적는다.

### 이슈 2. 이메일을 어떻게 믿나

**왜 문제인가.** 인증 없이 저장하면 오타나 남의 주소가 들어갈 수 있다. 그 주소로 재설정 메일을 보내면 엉뚱한 사람이 받는다.

**해결.** c-1에서는 이메일을 **저장만 하고 어디에도 쓰지 않는다.** c-2에서 인증 메일(링크를 눌러야 등록 완료)을 붙인 뒤에야 비밀번호 찾기에 연결한다. 이 숙제는 c-2로 넘긴다.

### 이슈 3. 탈퇴 때 데이터가 반쪽만 지워질 수 있다

**왜 문제인가.** `Vocabulary.articleId`처럼 `Article.userId`도 외래 키가 없는 숫자 칸이다. DB가 연쇄 삭제를 해 주지 않아서 계정만 지우면 글과 단어가 주인 없이 남는다(고아 데이터). 중간에 실패하면 일부만 지워진 상태가 될 수 있다.

**해결.** 서비스의 한 트랜잭션(전부 성공하거나 전부 취소되는 묶음) 안에서 **단어 → 글 → 계정** 순서로 지운다. 비밀번호가 틀리면 아무것도 지우지 않는다.

### 이슈 4. 가입 오류 처리가 너무 넓다

**왜 문제인가.** 지금 `UserController.signup`은 `IllegalStateException`을 넓게 잡아서 "이미 존재하는 아이디"로 처리한다. 이메일 중복이 추가되면 어떤 칸이 틀렸는지 구분되지 않고, 전혀 다른 원인의 `IllegalStateException`도 "중복 아이디"로 보인다(b 최종 리뷰에서 지적됨).

**해결.** `DuplicateUsernameException`, `DuplicateEmailException`을 따로 만들어 각각 해당 입력 칸에 오류를 붙인다.

## 4. 설계

### 4-1. 데이터

- `User`에 `email` 칸 하나를 추가한다(비워도 됨). 새 테이블은 없다.
- 지금은 `ddl-auto=update`가 칸을 자동으로 추가한다. 기존 회원의 `email`은 `null`이다.
- **이메일은 저장·중복 검사 전에 정리한다(정규화).** 서비스가 ① 앞뒤 공백을 제거하고 ② 소문자로 통일한 뒤 ③ 빈 값이면 `null`로 바꾼다. 이 정리된 값으로 중복 검사하고 저장한다. 그러지 않으면 `A@x.com`과 `a@x.com`, `a@x.com `(끝 공백)이 서로 다른 이메일로 취급돼 중복 불가 규칙이 우회되고, "이메일 없음"끼리 중복으로 걸린다.
- 정규화는 서비스(`UserService`)의 한 메서드에서만 하고, 가입·마이페이지 수정이 모두 그것을 거친다.
- 형식은 `@Email`(Bean Validation)로 검사하고, 중복 검사는 서비스에서 한다. 자기 자신의 이메일을 그대로 두고 저장하는 경우는 중복으로 보지 않는다.
- 소문자 통일은 이메일의 로컬 부분(`@` 앞)이 이론상 대소문자를 구분하지만 실제 서비스는 구분하지 않으므로, 중복 방지를 우선해 전체를 소문자로 한다.

### 4-1-1. 비밀번호 길이 규칙

지금 가입은 빈 값만 검사한다. 가입과 비밀번호 변경에 **같은 규칙**을 적용한다.

- **최소 8자.** 너무 짧은 비밀번호는 추측으로 뚫리기 쉽다.
- **최대 72바이트(UTF-8).** 비밀번호 암호화(BCrypt)는 앞의 72바이트만 사용한다. 그 뒤는 무시돼서, 그보다 길게 받으면 "긴 비밀번호를 설정했는데 앞 72바이트만 같으면 로그인되는" 착각을 만든다. 한글은 글자당 3바이트라 한글만으로 약 24자다. 사용자에게는 "8자 이상, 72바이트 이하(한글은 약 24자까지)"라고 안내한다.
- 규칙은 한 곳(예: 검증용 상수와 메서드 하나)에 두고 `SignupForm`과 비밀번호 변경 폼이 같이 쓴다. 두 곳이 어긋나지 않게 하기 위해서다.
- **기존 회원에게는 영향이 없다.** 이미 저장된 비밀번호는 그대로 로그인되고, 규칙은 **가입과 비밀번호 변경 때만** 검사한다.
- 계획 단계에서 Spring Security 7의 `BCryptPasswordEncoder`가 72바이트 초과를 예외로 막는지 확인하고, 막는다면 그 예외가 아니라 위 폼 검증이 먼저 걸리게 한다.

### 4-2. 코드 구조(기존 규칙 그대로)

- **Controller:** 새 `MyPageController`. 화면, 폼 검증 결과, 리다이렉트만 맡는다. 비즈니스 로직은 두지 않는다.
- **Service:** `UserService`에 `updateProfile`, `changePassword`, `withdraw`를 추가한다. 현재 비밀번호 확인, 이메일 중복 같은 규칙 판단은 여기서 한다.
- **Repository:**
  - `UserRepository`: `findByEmail`, `deleteById` 추가
  - `ArticleRepository`: `deleteByUserId` 추가(`findByUserId`는 이미 있음)
  - `VocabularyRepository`: `deleteByUserId` 추가(글의 `userId`를 거쳐 지운다)
  - 메서드를 추가하면 인터페이스, `jpa/` 어댑터, Spring Data 인터페이스, `memory/` 구현 4곳을 맞춘다.
- **`User` 엔티티:** 값을 바꾸는 메서드가 없으므로 `updateProfile(...)`, `changePassword(...)`를 추가한다. setter를 열지 않고 의미 있는 이름으로 바꾼다.
- **세션 갱신:** 컨트롤러 쪽 작은 도우미(`LoginUserRefresher`)가 새 `LoginUser`를 `SecurityContext`에 넣는다. 서비스는 Security를 몰라야 테스트가 쉽다.

### 4-3. 규칙

- **마이페이지 주소에는 id가 없다.** 로그인한 사용자 본인만 다루므로 남의 id로 접근하는 문제(IDOR)가 구조적으로 없다. 비로그인은 `/login`으로 보낸다(b와 같음).
- **비밀번호 변경:** 현재 비밀번호가 틀리면 폼에 오류 문구를 보여 준다. 새 비밀번호는 4-1-1의 길이 규칙(8자 이상, 72바이트 이하)을 따른다. 현재 브라우저의 세션 ID만 재발급하고, 다른 기기 세션은 유지된다(알려진 한계).
- **탈퇴:** 비밀번호 재입력 → 서비스가 단어 → 글 → 계정 삭제 → 컨트롤러가 현재 세션을 끊고 `/login`으로 보낸다. 다른 기기 세션은 남는다(알려진 한계). 남은 세션으로 글 저장은 막히지 않아 주인 없는 글이 생길 수 있다. 단어는 글 id가 아니라 **사용자 id로 한 번에** 지워 쿼리 수를 줄인다.
- 모든 폼은 `th:action`을 써서 CSRF 토큰이 자동으로 들어가게 한다.

## 5. Task 순서

작은 것부터 쌓는다. 각 Task는 "실패하는 테스트 → 최소 구현 → 통과"로 끝난다.

1. **이메일 칸:** `User.email` 추가, 가입 폼에 이메일(선택)과 안내문, 이메일 정규화(공백 제거·소문자·빈 값은 `null`), 중복·형식 검사, 중복 예외 두 개로 분리, 비밀번호 길이 규칙(가입에 먼저 적용; 기존 테스트의 짧은 비밀번호를 8자 이상으로 바꿔야 할 수 있다)
2. **마이페이지 조회·수정:** `/mypage` 화면, 닉네임·직군·이메일 수정, 상단 메뉴 링크
3. **세션 갱신:** 닉네임을 바꾸면 상단 닉네임이 바로 바뀐다
4. **비밀번호 변경:** 현재 비밀번호 확인, 같은 길이 규칙 적용, 현재 브라우저 세션 ID 재발급
5. **회원 탈퇴:** 가장 위험해서 마지막. 너무 커지면 이 Task만 뺄 수 있다

## 6. 테스트

- 이메일: 중복, 형식 오류, 자기 이메일 그대로 저장은 허용
- 이메일 정규화: 앞뒤 공백이 제거되고 소문자로 저장된다. `A@X.com`을 등록한 뒤 `a@x.com`으로 다른 계정이 등록하면 중복 오류다. 빈 값·공백뿐인 값은 `null`로 저장되고, `null`끼리는 중복이 아니다
- 비밀번호 길이: 7자는 거절, 8자는 허용, 72바이트는 허용, 73바이트(예: 한글 25자)는 거절. 가입과 비밀번호 변경 **두 곳에서 같은 결과**가 나온다. 기존 짧은 비밀번호로 로그인하는 것은 막히지 않는다
- 다른 기기 세션: 비밀번호를 바꿔도 다른 세션은 유지된다는 현재 동작을 문서화하는 테스트는 만들지 않는다(한계로 기록만 한다)
- 가입 중복 오류: 아이디 중복은 아이디 칸에, 이메일 중복은 이메일 칸에 붙는다
- 닉네임 변경 후 **같은 세션의 `LoginUser`가 새 닉네임**이고 상단 표시도 바뀐다
- 비밀번호 변경: 현재 비밀번호가 틀리면 실패하고 아무것도 안 바뀐다. 성공하면 새 비밀번호로 로그인할 수 있고 세션 ID가 바뀐다
- 탈퇴: **내 글·단어·계정만** 사라지고 다른 사용자의 것은 그대로다. 비밀번호가 틀리면 아무것도 안 지워진다. 이후 로그인할 수 없다
- 비로그인 접근은 `/login`으로, CSRF 토큰 없는 POST는 403이다
- 새 폼(마이페이지, 비밀번호 변경, 탈퇴)에 CSRF 숨은 필드가 있다

## 7. 사람이 직접 하는 일

- PR의 최종 리뷰와 머지
- **배포 시 주의**
  - `user` 테이블에 `email` 칸이 하나 추가된다. `ddl-auto=update`가 자동으로 반영하고 기존 회원은 `null`이다. 되돌릴 때도 칸을 그대로 둬도 앱은 동작한다.
  - 강제 재로그인은 없다(b와 다름).
  - 새 비밀번호 길이 규칙(8자 이상, 72바이트 이하)은 가입·변경 때만 적용된다. 기존 회원의 로그인은 영향이 없다.
  - 비밀번호를 바꾸거나 탈퇴해도 **다른 기기의 로그인 세션은 유지된다**(알려진 한계).
  - **탈퇴는 복구가 안 된다.** 배포 후 테스트 계정으로만 확인한다.
- 배포 후 확인: 가입(이메일 있음/없음), 마이페이지 수정, 비밀번호 변경 후 재로그인, 테스트 계정 탈퇴

## 8. 위험

- **`SecurityContext` 교체 방식이 Spring Security 7에서 달라졌을 수 있다.** 계획 단계에서 실제 API를 확인하고, 교체 후 같은 세션의 다음 요청에서 새 값이 보이는지 테스트로 증명한다.
- **탈퇴 삭제 순서가 틀리면 고아 데이터가 남는다.** "다른 사용자의 것은 그대로" 테스트가 이 위험을 잡는다.
- **인증 전 이메일 선점.** 남의 이메일을 먼저 등록할 수 있다. c-1에서는 이메일을 어디에도 쓰지 않아 피해가 없고, c-2 인증으로 풀린다.

## 9. 완료 기준

1. 가입 폼과 마이페이지에서 이메일을 선택적으로 등록·수정할 수 있고, 중복·형식 오류는 해당 칸에 표시된다(테스트).
2. 닉네임을 바꾸면 같은 세션의 상단 닉네임이 바로 바뀐다(테스트).
3. 비밀번호 변경은 현재 비밀번호를 확인하고, 성공하면 현재 브라우저의 세션 ID가 바뀐다(테스트). 다른 기기 세션 유지는 알려진 한계로 기록돼 있다.
   3-1. 이메일은 공백 제거·소문자 통일 후 저장·중복 검사되고, 빈 값은 `null`이다(테스트).
   3-2. 비밀번호는 8자 이상 72바이트 이하이고 가입·변경에 같은 규칙이 적용된다(테스트).
4. 탈퇴하면 본인의 글·단어·계정이 한 트랜잭션에서 지워지고 다른 사용자의 데이터는 그대로다(테스트).
5. 가입 오류가 `DuplicateUsernameException`·`DuplicateEmailException`으로 구분된다(테스트).
6. 비로그인은 `/login`으로, CSRF 없는 POST는 403이다(테스트).
7. CI(`code-quality`)가 통과한다.
8. README의 c 행이 c-1, c-2, c-3으로 나뉘어 있고, c-2로 넘기는 숙제(이메일 소유 확인)가 기록돼 있다.

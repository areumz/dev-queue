# v2-0b 버그·보안 수정 + 최소 Spring Security 설계

> 상위 문서: [v2-0 개요](README.md)
> 목표: 로그인한 사용자가 **자기 데이터만** 보고 고칠 수 있고, 다른 사이트가 사용자 몰래 요청을 보낼 수 없다. 브리프 1장의 코드 버그를 함께 고친다.

---

## 0. 이번 단계의 목적

지금 DevQueue는 "로그인했는지"만 확인하고 "누구 것인지"는 거의 확인하지 않는다. 그래서 로그인한 사람이 URL의 숫자만 바꾸면 남의 글을 지우거나 고칠 수 있다. 이번 단계는 이 구멍을 막는 것이 핵심이다.

v2-1에서 REST API, 크롬 확장 프로그램이 붙으면 요청이 들어오는 입구가 늘어난다. 입구가 늘기 전에 "로그인 확인 → 주인 확인" 규칙을 한 곳에 세워 둔다. 마이페이지, SNS 로그인 같은 기능은 c에서 이 위에 얹는다.

---

## 1. 범위

**넣는 것** (브리프 1장 기준)
- 보안: IDOR, CSRF, URL 스킴 검증, 세션에 엔티티 저장
- 로직: 팝업 암기 토글, Category 누락, 삭제 시 고아 단어, 타임존
- 구조: `findAll()` 후 메모리 필터, 단어 N+1, 전역 예외 처리
- 정리: 안 쓰는 코드(`findByCategory`, hello 파일), Tabler CDN `@latest` 고정

**빼는 것**
- **운영 설정**(`ddl-auto=update`, `show-sql`) → **d로 미룬다.** 이걸 바꾸려면 DB 변경 이력 도구(Flyway)가 필요하다. b는 테이블 구조를 바꾸지 않고, d의 `user_event`가 첫 테이블 추가라서 Flyway를 들이기에 자연스럽다.
- **배포**(HTTPS, systemd/Docker, RDS 퍼블릭 차단) → 코드가 아니라 서버 작업이다. 별도 인프라 사이클로 뺀다.
- 마이페이지, 비밀번호 찾기, SNS 로그인 → c
- REST API용 인증 구조(브리프 4장 열린 질문 1) → v2-1
- **`username` 유니크 제약** → d. 지금 `username` 컬럼에는 DB 유니크 제약이 없다. 그래서 두 사람이 동시에 같은 아이디로 가입하면 중복이 생길 수 있다(b의 중복 검사는 "먼저 조회 후 저장"이라 동시 요청을 못 막는다). 제약을 걸려면 테이블 구조를 바꿔야 해서 이번 범위 밖이다. 이미 중복된 아이디가 있으면 제약 추가가 실패하므로, 운영 DB를 먼저 확인한 뒤 Flyway와 함께 d에서 처리한다.
- **세션의 `LoginUser` 갱신** → c 메모. 세션의 `LoginUser`는 로그인 시점의 복사본이다. c에서 닉네임을 바꾸면 DB만 바뀌고 화면 상단 닉네임은 다음 로그인까지 옛 값으로 남는다. 닉네임 변경 시 세션의 `LoginUser`도 같이 갱신해야 한다.

## 2. 최소 Spring Security

### 2-1. 무엇을 바꾸나

| 지금 | 바뀐 후 |
|---|---|
| `LoginCheckInterceptor`가 세션에 `loginUser`가 있는지 확인 | Security가 확인한다. 인터셉터와 `WebConfig`는 지운다. |
| `UserController.login()`이 직접 비밀번호를 확인하고 세션에 `User` 저장 | Security의 **폼 로그인**이 처리한다. 비밀번호 확인은 `UserDetailsService`(아이디로 사용자를 찾아 주는 클래스) 하나만 만들면 된다. |
| 세션에 `User` 엔티티(비밀번호 해시 포함) | 세션에는 `LoginUser`(id, username, nickname)만 담긴다. 비밀번호 해시는 담지 않는다. |
| CSRF 방어 없음 | Security 기본값으로 켜진다. Thymeleaf의 `th:action` 폼에는 토큰이 자동으로 들어간다. |
| 로그인해도 세션 ID 그대로 | Security가 로그인 순간 세션 ID를 새로 발급한다(기본값). |
| 로그아웃: 컨트롤러가 세션 삭제 | Security의 `POST /logout`이 처리한다. |

### 2-2. 동작 규칙

- 로그인 없이 열 수 있는 주소: `/login`, `/signup`, `/css/**`, `/js/**`, `/error`. 앞의 4개는 지금 인터셉터가 열어 둔 것과 같고(대조 완료), **`/error`만 새로 연다.** Security는 에러 화면 요청에도 로그인 검사를 하기 때문에, `/error`를 안 열면 로그아웃 상태의 에러 화면(403 등)이 전부 `/login`으로 튕긴다. 나머지는 로그인이 필요하고, 안 했으면 `/login`으로 보낸다(지금과 같음).
- 로그인 성공 → `/articles`. 실패 → `/login?error`, 화면에 "아이디 또는 비밀번호가 올바르지 않습니다."
- 회원가입 후 "회원가입이 완료되었습니다" 메시지는 지금처럼 유지한다.
- `login.html`의 `<form action="/login">`은 `th:action="@{/login}"`으로 바꾼다. 안 바꾸면 CSRF 토큰이 안 들어가서 로그인이 403으로 막힌다.
- 컨트롤러는 로그인 사용자를 `@AuthenticationPrincipal LoginUser`로 받는다. `request.getSession()`을 직접 꺼내는 코드는 모두 사라진다.
- `LoginUser`는 인증할 때는 비밀번호 해시를 들고 있다가, 로그인 성공 직후 Security가 지운다(`CredentialsContainer`). 세션에 저장되므로 `Serializable`이어야 하는데, `UserDetails`가 이미 이를 요구하고 필드가 `Long`·`String`뿐이라 문제없다. 테스트로 직렬화·비밀번호 지움을 확인한다.
- `articles.html`의 닉네임 표시(`loginUser.nickname`)는 컨트롤러가 모델에 넣는 `loginUser` 속성에 의존한다(닉네임을 쓰는 곳은 이 한 군데뿐). 이 모델 속성은 `@AuthenticationPrincipal`로 받은 `LoginUser`로 계속 넣는다. Security용 Thymeleaf 태그 라이브러리는 새로 들이지 않는다.
- 팝업 날짜(`lastPopupDate`)는 세션 값이 아니라 DB에서 읽는다. 세션과 DB가 어긋나는 문제가 같이 없어진다.
- `PasswordEncoder` Bean은 그대로 둔다. 기존 BCrypt 해시가 그대로 맞으므로 **기존 회원은 다시 가입하지 않아도 된다.** 배포 직후 로그인돼 있던 사람은 한 번 다시 로그인해야 한다.
- `spring-security-crypto` 단독 의존성은 Security 스타터에 포함되므로 지운다.

## 3. 소유권 검증 (IDOR)

### 3-1. 규칙

- **주인 확인은 Service에서 한다.** Service 메서드가 로그인 사용자 id를 받고, 주인이 아니면 예외를 던진다. 컨트롤러가 확인을 빼먹어도 Service를 거치면 막힌다. v2-1의 REST API도 같은 Service를 쓴다.
- **남의 것과 없는 것을 똑같이 404로 응답한다.** 403(권한 없음)으로 응답하면 "그 번호의 글이 존재한다"는 사실이 새어 나간다.
- 단어는 자기 글을 거쳐서 주인을 확인한다(단어 → 글 → 글의 `userId`).

### 3-2. 막아야 할 요청

| 요청 | 지금 |
|---|---|
| `GET /articles/{id}` | 검사함. 다만 남의 글이면 500이 난다 → 404로 바꾼다 |
| `GET /articles/{id}/edit` | **검사 안 함** (브리프 목록에 없던 것, 이번에 발견) |
| `POST /articles/{id}/edit`, `/delete`, `/memo`, `/read` | 검사 안 함 |
| `POST /articles/{id}/vocabularies` (남의 글에 단어 추가) | 검사 안 함 |
| `POST /vocabularies/{id}/toggle`, `/delete` | 검사 안 함 |
| `POST /vocabularies/memorize` (ids 중 남의 단어) | 검사 안 함. 남의 id가 하나라도 섞이면 **전체를 404로 거절**하고 아무것도 바꾸지 않는다 |

### 3-3. 순서 (TDD)

1. **Spring Security를 먼저 넣는다(2장).** IDOR 테스트를 옛 로그인 방식으로 쓰면 Security를 넣은 뒤 전부 다시 써야 하기 때문이다. 그래야 "수정 전" 실패도 주인 확인 누락 하나만 보여 준다.
2. 위 요청마다 "로그인한 A가 B의 리소스에 요청 → 404, B의 데이터는 그대로"인 테스트를 새 로그인 도우미와 CSRF 토큰으로 쓴다.
3. 전부 실패하는 것을 확인하고, 그 결과를 PR 본문에 남긴다(수정 전 증거). 실패 상태로는 커밋하지 않는다.
4. 고쳐서 통과시킨다.

- "없음/남의 것" 예외의 404 응답은 PR 1에서 바로 붙인다(예외 클래스에 `@ResponseStatus`). 테스트가 404를 확인해야 하기 때문이다. 404 화면 템플릿은 PR 2에서 만든다.
- 단어 토글·삭제 후 돌아갈 글은 폼이 보내는 `articleId` 값이 아니라 단어의 실제 글에서 정한다. 사용자가 보내는 값은 바꿔치기할 수 있다.

## 4. 입력·로직 버그

| 문제 | 고친 후 |
|---|---|
| **URL에 `javascript:` 저장** | 글 저장·수정 시 Service가 URL을 검사한다. **빈 값, 공백뿐인 값, 호스트가 없는 값, `http`/`https`가 아닌 스킴**은 거절하고(운영 DB에 빈 URL 글이 4건 있다 = 지금까지 입력 검사가 없었다는 증거), 폼을 다시 보여 주며 "http 또는 https 주소만 저장할 수 있어요"를 띄운다. 입력한 값은 폼에 남긴다. |
| **팝업 "확인"이 상태를 뒤집음** | `markMemorized`(항상 true로 설정)를 쓴다. 두 번 제출해도 결과가 같다. 상세 화면의 토글 버튼은 원래 토글이 맞으니 그대로 둔다. |
| **수정 시 Category 누락** | 수정 폼에서 카테고리를 필수로 받는다. 빠지면 400으로 응답하고 저장하지 않는다. |
| **글 삭제 후 단어가 남음** | 글을 지울 때 그 글의 단어도 **같은 트랜잭션에서** 지운다. 하나라도 실패하면 둘 다 취소된다. |
| **하루가 KST 오전 9시에 바뀜** | "오늘"을 `Asia/Seoul` 기준으로 계산한다. `Clock` Bean(현재 시각을 알려 주는 객체)을 하나 등록해서 쓴다. 테스트에서 시각을 고정할 수 있어서 "자정 직후" 같은 경계를 검증할 수 있다. |
| **같은 아이디로 가입하면 500** | (브리프 밖, 이번에 발견) 가입 폼에 "이미 존재하는 아이디입니다"를 띄운다. |

## 5. 조회 개선

- `findMyArticles`: 전체 글을 가져와 Java에서 거르던 것을 DB에서 거른다(사용자 id + 카테고리 조건 조회).
- 안 외운 단어: 글마다 쿼리를 날리던 것(N+1)을 JPQL 한 번으로 바꾼다. 3개를 고르는 방식(DB에서 무작위 vs Java에서 섞기)은 구현자가 정한다.
- Repository 인터페이스에 메서드를 추가하면 `jpa/` 구현과 `memory/` 구현 둘 다 맞춘다(컴파일이 깨지지 않게).
- **개선 전후 쿼리 수를 숫자로 남긴다.** 글 10개, 글마다 단어 3개인 사용자로 목록 화면을 열었을 때의 쿼리 수를 측정해 PR 본문에 적는다. **오늘의 단어 팝업이 뜨는 상황으로 측정한다.** N+1은 팝업 단어를 고를 때만 생기고, 팝업은 하루 한 번만 뜨기 때문이다. 테스트에서 `Clock`과 `lastPopupDate`로 이 상황을 고정한다.

## 6. 에러 처리

- "없음/남의 것" 예외 하나(`ResourceNotFoundException` 같은 이름)를 만들고 404로 응답한다.
- 에러 화면 템플릿을 둔다: 403("세션이 만료됐어요. 다시 로그인해 주세요"), 404("찾을 수 없는 페이지예요"), 400("요청이 올바르지 않아요"), 500("잠시 후 다시 시도해 주세요"). 404·400·500은 목록으로, 403은 로그인으로 돌아가는 링크를 둔다.
- **403 화면은 PR 1에 넣는다.** CSRF 검사에 실패하면(세션이 만료된 뒤 열려 있던 폼을 제출하는 경우 등) 403이 나는데, CSRF는 PR 1에서 켜지므로 PR 1 배포 직후부터 사용자가 볼 수 있다. 나머지 화면은 PR 2.
- 화면 템플릿은 `/error` 요청에 상태 코드를 흉내 내서 테스트한다(`BasicErrorController`가 `error/<상태코드>.html`을 고른다). 구현해 보고 이 방식이 안 되면 수동 확인으로 대체하고 PR 본문에 적는다.
- Spring Boot는 `templates/error/404.html` 같은 파일을 상태 코드별로 자동으로 찾아 쓴다. 그래서 `@ControllerAdvice`는 **이 방식으로 부족할 때만** 만든다(구현자 판단).
- 500 화면에 예외 메시지나 스택을 노출하지 않는다.

## 8. 테스트 방식 변경

- `TestSessions.loginAs(user)` → Security 방식 도우미로 바꾼다. MockMvc 요청에 `LoginUser` principal을 붙이는 형태다(`spring-security-test` 사용). 파일 하나에만 둔다.
- 모든 POST 테스트에 CSRF 토큰을 붙인다. 그리고 **"토큰 없는 POST는 403"** 테스트를 하나 둔다. 이 테스트가 CSRF 방어가 켜져 있다는 증거다.
- **폼 화면 CSRF 숨은 필드 테스트:** 로그인, 회원가입, 글 작성·수정, 글 상세(메모·읽음·단어 추가·토글·삭제), 오늘의 단어 팝업, 로그아웃 폼을 GET으로 열어 모든 폼에 `name="_csrf"` 필드가 있는지 확인한다. POST 테스트는 `.with(csrf())`를 직접 붙이기 때문에 `th:action`이 빠진 폼을 잡지 못한다. 이 테스트가 그 빈틈을 메운다.
- 실제 로그인 흐름 테스트: 맞는 비밀번호 → `/articles`로 이동, 틀린 비밀번호 → `/login?error`, 로그인 전후 세션 ID가 다르다.
- `CLAUDE.md`의 테스트 규칙(로그인 흉내 방법, POST에는 CSRF)을 새 방식으로 고친다.

- 머지 후 EC2에 배포하고 직접 확인: 로그인, 글 저장, 단어 팝업, 로그아웃
- **배포 계획:** PR 1 머지 직후 배포한다(보안 수정이 목적이라 미룰 이유가 없다). 배포하면 로그인돼 있던 사람은 한 번 다시 로그인해야 한다. PR 2는 따로 배포한다. 이 내용을 PR 1 본문에 적는다.
- 운영 DB에 이미 들어간 문제 데이터 확인
  - **URL이 빈 값인 글: 4건 확인됨.** 새 규칙은 이 글을 지우거나 바꾸지 않는다. 다만 **이 글의 수정 화면에서 저장하려면 URL을 채워야 한다**(빈 URL은 거절되므로). 메모 수정, 읽음 표시, 단어 관리는 URL 검사와 무관해서 그대로 된다. 4건을 직접 고칠지, 그대로 둘지 정한다.
  - `javascript:`로 시작하는 URL이 있는지
  - 지워진 글에 매달린 고아 단어가 있는지
  - 있으면 어떻게 처리할지 정한다. 이번 코드는 **새로 생기는 것만** 막는다.

## 12. 위험

- **Spring Boot 4에서 Security 설정 문법이나 의존성 이름이 바뀌었을 수 있다.** 계획 단계에서 실제 이름(`spring-boot-starter-security`, 테스트용 모듈)을 확인하고 고정한다.
- **폼 중 하나라도 `th:action`이 아니면 그 기능이 403으로 막힌다.** 지금 확인된 곳은 `login.html` 하나다. 모든 폼을 테스트로 한 번씩 지나가게 해서 잡는다.
- **배포 직후 로그인 상태가 풀린다.** 세션에 담는 객체 모양이 바뀌기 때문이다. 사용자가 거의 없어서 받아들인다.

## 13. 완료 기준

1. 3-2의 모든 요청에 대해 "A가 B의 리소스 요청 → 404, B 데이터 그대로" 테스트가 있고 통과한다. 수정 전 실패 기록이 PR 1 본문에 있다.
2. CSRF 토큰 없는 POST는 403이다(테스트).
3. 로그인 전후 세션 ID가 다르다(테스트). 세션에 `User` 엔티티가 없다.
4. `javascript:` URL, 빈 URL, 공백뿐인 URL은 저장·수정 모두 거절된다(테스트).
5. 4장의 로직 버그마다 재현 테스트가 있고 통과한다.
6. 목록 화면 쿼리 수 전/후가 PR 2 본문에 숫자로 있다.
7. 남의 것·없는 것은 404 화면, 잘못된 요청은 400 화면이 뜬다.
8. CI(`code-quality`)가 통과한다. SpotBugs 제외 목록의 v2-0b 항목이 없다.
9. ADR 2개가 있고, `CLAUDE.md`의 테스트 규칙이 새 방식으로 바뀌어 있다.
10. 모든 폼 화면에 CSRF 숨은 필드가 들어 있다(테스트). `LoginUser`는 직렬화되고 인증 후 비밀번호가 지워진다(테스트).
11. 로그아웃 상태에서 `/error`가 `/login`으로 튕기지 않고, CSRF 실패 때 403 화면에 "세션이 만료됐어요. 다시 로그인해 주세요"가 보인다(테스트).
